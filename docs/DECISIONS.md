# 双工具协作：DECISIONS

## 边界规则（先读）

- 🔴 ChatGPT 红线区（只做这些）：架构契约、Agent Loop+双通道、安全门、Playwright 核心、关键复核、疑难会诊。
- 🔵 WorkBuddy 蓝区（其余全部）：UI、标准工具、Provider preset、HA REST、测试、文档、常规修复。
- 冲突规则：默认归 WorkBuddy；WorkBuddy 不擅改红线区（只能提建议）；ChatGPT 不代改蓝区（只标注）。
- 本次交接文档初始化与测试是用户明确授权的单次工作；不扩大日常职责。当前暂停新增功能。

## 已确定的决策

下列记录于 **2026-10-16 ~ 2026-10-17**，依据用户指示与源码盘点；“已定”表示约束有效，不表示全部代码已实现或验收。

| ID | 决策 | 执行含义 / 依据 |
|---|---|---|
| D01 | 红区最小化，默认蓝区 | 红区合并为 TASKS 的 R01–R03；测试、文档、常规实现不因位于 core/main 就归红 |
| D02 | 暂停新功能，先建立交接 | 本轮只改四份文档并运行测试；待办中的功能项维持暂停，恢复范围由用户确定 |
| D03 | 保留四层架构与可切换 Provider 契约 | 复用现有 Agent、情绪、日记、关系、RAG、提醒；不做整体重写 |
| D04 | 真实经历优先，用户能解释、停止、纠错、忘记、导出 | 来源、时间、删除状态必须传递到召回和年鉴；事实、主观记录、创作分别展示；不虚构感知，不设计催促、挽留或愧疚机制 |
| D05 | 只录入之后的新日记 | 用户明确选择；不把旧日记批量补录入 RAG。旧数据迁移/账本索引不能改变这一限制 |
| D06 | 保留当前语音配置 | 用户明确要求；延迟测量和候选适配器工作不得悄悄切换引擎或音色。注册表桩不算已实现 |
| D07 | 敏感场景启用有限重试人格护栏 | 用户已选“加入有限重试护栏”；接受敏感回复缓冲带来的延迟。人格以 v2 为唯一基准，禁止靠固定回复掩盖模型失败 |
| D08 | 本地模型默认切换需证据 | 多轮人格、事实边界、工具结果与延迟验收后做关键复核；当前不能凭单次通过或旧文档宣称已达标 |
| D09 | 授权与操作完成必须可核查 | 按操作和目标授权；撤销/取消应及时生效；承诺完成需结果证据，重试不能重复外部动作 |
| D10 | 保留他人的未提交改动 | 进入本轮已存在 cloud-config.js 差异；由原修改者/WorkBuddy 处理，不把内容抄入文档或混入提交 |
| D11 | 验收按实际结果记账 | 本轮 347 项中 345 通过、0 失败、2 跳过；退出码绿灯不代表链接安全、真实设备和安装包人工验收已完成 |
| D12 | 一个任务一个修改者，按职责拆跨界改动 | TASKS 领取与交接；蓝区需要红区改动时只提建议，红区发现蓝区问题只标注；禁止并行改同一文件 |
| D13 | 外部原生子进程的路径参数必须 ASCII 可达 | 传统 `main()` C 程序（如 sherpa-onnx WS 服务）的 argv 按系统 ANSI 代码页（中文系统 cp936/GBK）转换，非 ASCII 路径（如 userData 含「凪」）会变乱码致服务启动即退；对策：cwd=目标目录 + 纯 ASCII 相对路径参数，兜底为 `%TEMP%` ASCII 镜像（硬链接）。powershell.exe 等 wmain Unicode 原生程序不受此限 |
| D14 | Live2D 资源磁盘名一律 ASCII，显示名保留原名 | 模型经 `nagi-local://` 拼 URL 再落 Windows 路径，中文文件名会被编码打坏（缅因交付包内已有文件名被打成 `[M%_O$@6(OU@R@SXLWP`N_G.png`）。故磁盘上用 `Maine/`、`blush.exp3.json`，`model3.json` 的 `Name` 仍写中文，UI/接口看到的是中文 |
| D15 | 取景带按模型分别标定，不共用一套 magic number | 不同模型美术范围差异很大（缅因横向只占 0.273~0.813，套通用 0.11~0.95 会被 contain 缩到 0.095）。`src/core/frame.js` 用 `FRAME_PROFILES` + `frameProfile(frame, modelName)` 匹配；换模型必须重新跑探针标定，命中不到回落通用预设 |
| D18 | 装束走**参数保持层**，不用表情实现 | Live2D 的 expression 是**独占**的——点「眼镜」表情会把当前情绪表情顶掉。装束要与情绪面容并存，只能由渲染层在 `beforeModelUpdate` 里以绝对值写参数（`setParameterValueById`，压过动作/表情写的 0，否则动作每帧把配件写回 0 会一闪一闪）。这是第 4 个 beforeModelUpdate 钩子，与 redGuard／poseHook／rhythmHook 并存 |
| D19 | 微注视是对 2026-10-15「取消跟随鼠标」的**修订**，不是推翻 | 当时取消的是"鼠标停哪儿她盯哪儿"的机械跟随；现在加回的是**有节制的高光行为**：明显移动才触发、距上次 >6s、看 1.6~2.8s 就移开、鼠标静止不追、她说话/播动作/夜间静默时根本不看、静默时强制归中。因此 verify:pose 的"焦点控制器不跟随鼠标"仍然成立（验证实例带勿扰，注视不触发） |
| D20 | 注视只广播**方向**，绝不广播坐标 | 主进程 400ms 采样光标后立刻化成 `(x,y)∈[-1,1]` 的相对方向再广播，渲染层拿不到也存不下"鼠标在第几像素"。不落盘、不进记忆、不给模型看；受 `privacy.doNotDisturb`／`monitorEnabled` 约束，鼠标不动就不发 |
| D21 | 全局热键属于**本地触发**，不走安全门确认 | 安全门管的是"模型请求做外部动作"；热键是用户自己按的，且桌宠是 `skipTaskbar + showInactive` 的悬浮窗、收不到普通键盘事件，只能在系统层注册。热键开关即时生效（设置保存后重新注册），某个组合被占用只报不阻塞其它 |
| D16 | Live2D 贴图最大边长 4096，超出即降采样 | 桌宠常驻时贴图是显存与启动耗时的大头：缅因原包 8192×8192 ×3 = 768MB 显存 / 94MB 磁盘 / 冷启动 6.4s。降到 4096 后 192MB / 13.5MB / 2.8s，PSNR 35.8~37.0dB 肉眼基本无感（桌宠最大窗 900×1300 时形象只画 751×901 px，4096 仍属过剩采样）。用 `scripts/shrink-textures.py`（先 `--scan`）；**原图一律归档不删**，改 `model3.json` 的 `FileReferences.Textures` 切目录。路径必须正斜杠（D14）——脚本曾用 `os.path.join` 写出反斜杠，在 `nagi-local://` URL 里会出问题 |
| D22 | 渲染层的"画面差分"验证必须块级降采样 + 先冻结她自身的动态 | 待机动作/呼吸/眨眼每帧都在变，逐像素比较会把任意两次抓帧算成"差 20%+"，于是"画面变了"这种判据既能假通过（姿态漂移）也会假失败。做法：① 把画面降采样成 24×24 块（按 alpha 加权）再比，抗锯齿边缘的 1px 抖动被平均掉；② 抓帧前用 `freezeIdleMotion(true)` 按住待机摆动/呼吸/眨眼参数，并**自检静置抖动**（应 <5%）。另：`readParams` 读的那份参数数组**读不到表情/眨眼那一层**（deepProbe 实测 mirror=0/live=undefined/core=no-method），拿它做"表情是否生效"的判据是假通过 |
| D34 | 眨眼必须**自己排**，不能依赖框架 | 框架（cubism4.js）里眨眼只在"这一帧没有动作在更新"时才跑：`const motionUpdated = motionManager.update(...)` → `if (!motionUpdated) eyeBlink.updateParameters(...)`。而 Idle 动作是常驻循环（nagi_idle 9 秒一轮），motionUpdated 恒为 true → **她一次都不会眨眼**。用户 2026-10-17 直接指出"似乎没看到眨眼"，就是这个。改为 `core/face/blink.js` 自排：间隔 2.2~5.6 秒、闭得快开得慢（85/35/155ms）、约 12% 连眨两下。写入时**乘在当前值上**（不是直接写 1/0），这样笑眼等表情造成的半闭不会被抹掉。 |
| D35 | 头转的时候**眼珠必须跟着转** | 头转 30° 而眼珠不动，看起来是"面无表情地侧着脸"；眼珠偏 0.45（值域 ±1）才有"目光落过来"的感觉。转向层里用 set 同时写 `ParamEyeBallX/Y`；待机头部摆动时用 add 补 0.35 的比例（否则眼珠相对眼眶像在飘，斜视感）。注意 `Param66/67 眼球深度` 由物理自动跟随（PhysicsSetting18/19 输入就是 `ParamEyeBallX/Y + ParamAngleX/Y`），不用手写。 |
| D36 | 灵动感来自**节奏对比**，不是均速 | 原来动作是"每 5~10 分钟一次"，均匀得像节拍器。改成簇发：一次动作后有 34% 概率在 18~42 秒内再来一个（最多连着 2 个），簇尾**强制**回到长安静。另外"安静很久（≥4× 待机阈值）之后的第一个动作"标记为 big，渲染层优先选挥手/欢呼这种明显的动作。核心是「少而重 vs 密而轻」的对比，而不是整体变密。 |
| D37 | 配置里的表情引用必须是模型 **Name**，且这条要静态锁 | `resolveExpression` 用 `model3.json` 的 `Name` 匹配，而 `nagi-emotion.json` 曾把 smile 填成文件名 `blush`、worry 填成 `nervous_sweat`（这两个表情的 Name 是「脸红」「紧张汗」）→ 解析静默返回 null，**微笑/担心两张脸彻底不出现且不报错**。修法：① 映射改真名（smile→`nagi_smile`、worry→`紧张汗`）；② `test/face-expression.test.js` 增加静态锁——每个映射条目的 expr 必须是模型里真实存在的 Name，且必须在 `nagi-face.json` 有对应肌肉向量。教训与 D14 同源：**两类命名（磁盘文件名 vs 模型内 Name）在交接处必须显式转换或显式校验**。 |
| D38 | 验收判据读"真正写入的值"，且必须区分**新鲜写入**与**陈旧残留**（seq 过滤） | 像素差分在低帧率+物理余震下不可信（D32 时代已踩），改读写入值后还有第二层坑：钩子早退时**不写**，读到的上次值会一直躺在那儿——verify:turns A 的"关"窗曾读到 \|z\|=4.68° 残尾（关掉瞬间正好有转向在飞）；D 项读 DOM 气泡则 8 个全空（气泡 6 秒自动隐藏、非桌宠形态不显示）。修法：写入值带 `seq` 序号，验收只认"切换之后的新鲜帧"（不足 3 帧不判）；气泡改读渲染层记的历史（`__nagiPokeBubbles`）。同类：verify:face H 的随机采样窗口要给分布留余量（游走 6 秒窗实测跨度 0.24~0.34 卡在阈值 0.35 上，拉到 10 秒后 0.59~0.67）。 |
| D39 | 姿态（思考）激活时，眼球游走必须让位 | 钩子链顺序 pose→…→eye，pose 用 **add** 写 `ParamEyeBall*`，eye 游走用 **set** 且排在后面——不躲开会把姿态的目光偏移整个盖掉：思考时她的目光会自己飘走，verify:pose 抓到 ΔEyeBallX=0.468 而非姿态目标 0.35（差值正是游走落点）。以前没暴露是因为游走有"页面加载头 6 秒让位"的 gate，验收碰巧全跑在 6 秒内；启动一慢就翻车。修法：`eyeWanderHook` 里 `if (poseState) return`（与让位 turnCtl 同款纪律）；验收侧再按住游走双保险（"测一层必须按住其它层"）。 |
| D40 | 验收脚本的期望表必须**实读配置**，脚本自身要满足环境硬约束 | 两个静默烂掉的验收：① verify:maine / verify:maine-live 的情绪映射表是硬编码的（`smile: '脸红'`），D37 改配置后没同步，而检查只验"表情存在可应用"不对比配置——C 项一直绿着但验的早已不是现行映射。修法：映射从 `nagi-emotion.json` 实读（读不到才退回内置表）。② verify:pose 是全仓唯一漏了 `NAGI_RENDERER_SANDBOX=0` 的 verify 脚本，本机 GPU 进程必崩 →"桌宠页未就绪"连续超时。教训：**验收代码也是代码，会腐烂；期望值与配置同源的必须实读，环境开关逐脚本自查**。 |
| D41 | 语音「情绪差异」不能只验方向性，还要验**幅度下限**；且「新表默认不生效」必须显式记录，不许靠猜 | OBS-1（真机「情绪起伏偏弱、整体过于含蓄」）后只调 `VOICE_PROFILE` 数值。原单测只有方向性断言（`joy.rate > calm.rate`）——**方向对而幅度被调小，它照样全绿**，这正是旧表 joy 只比 calm 快 8、0.5 强度塌到 4 却长期无人发现的原因。补断言：任意两情绪至少一轴差 ≥5、两极语速差 ≥25、joy>smile>calm 与 pout<worry<calm 序关系、半强度差 >4。同时查明 `presence.voiceProfileEnabled` 默认 **false**，默认路径走的是 `MOOD_SPEECH`——**只改新表在默认配置下听不到任何变化**（已上报用户裁决，未擅自改默认开关或旧表） |
| D42 | 加分项 C/D：语气音要防的是「变口头禅」而不是「听感怪」；时间线排序必须是 core 纯函数 | C（回合首尾语气音）真正的风险不是念起来怪，是**频率失控**：所以概率上限 0.3 在 core 里夹死（不只靠设置页滑块 max=30）、每天 ≤4 次、最小间隔 3 分钟、深夜与勿扰一律不出声、默认 `enabled:false`+`probability:0`，且写单测盯着出厂默认。**轻笑不做**——文本 TTS 念「呵」是音节不是笑声，真笑声要引入音频素材（= 新依赖，违反「不加新引擎/新依赖」），这条如实写在模块注释而不是假装做了。D（回忆时间线）的排序与按天分组放在 `core/presence/anchors.js`（纯函数 + 5 项单测），渲染层只负责画；时间缺失的排最后且**不补默认值**（不猜时间） |
| D51 | 六情绪的语音偏移**只允许存在一份**；「切开关」可以改变维度，不许改变性格 | OBS-1（用户听「情绪起伏偏弱」）后只加大了新表 `VOICE_PROFILE`，旧表 `MOOD_SPEECH` 一直是另一份小一截的数字（joy 只 +8）且 `worry` 方向相反（旧「略快」/ 新「放慢低沉」）——而走哪张表由「语音情绪映射」开关决定，于是用户切一下开关就像换了个人。用户裁决 A（拉齐旧表）后没有去"把旧表抄一遍"，而是新增 `src/core/voice/mood-table.js` 作唯一出处，两表都从它深拷贝：**备忘挡不住漂移，单一出处才挡得住**（同类教训见 D40/D45）。维度差别如实保留：新表有强度缩放/昼夜时段/语气标记，旧表只有情绪本身、且从不因情绪改音量（设计而非遗漏）。单测补两条硬断言：旧表幅度下限（任意两情绪至少一轴 ≥5、两极语速 ≥25、两个方向单调）与**跨表一致性**（满强度下两表 rate/pitch 完全相等）——后者才是"切开关不换人"的守门人 |

| D44 | 外部便签写入（B23）main 接线：全项目**只有一个地方 fs 写盘**，且每次写入都要逐次确认；`wx` 而不是 `w` | 桥接收敛在 `src/main/notes-file.js`：目录只能由**系统目录选择器**选出（不接受手填——手填就可被引诱到任意位置），选出后立刻 `realpathSync` 存真实路径；写入前把 core 的路径校验**再跑一遍**（带真实 `realpathSync`），不过绝不写；`fs.writeFile(..., {flag:'wx'})`——**已存在就失败**，绝不覆盖用户已有的文件（幂等表只存内存、重启归零，靠 `wx` 兜底，这条是刻意的：落盘会让它"跨天还记得写过什么"）。写完之前弹**原生确认框**（`['写入','取消']`，默认/取消都是"取消"，**不提供"以后都不问"**——逐次授权是这个功能能被允许存在的代价）。失败一律如实返回 reason（`disabled`/`no-root`/`no-note`/`duplicate`/`too-soon`/`write-failed`），界面绝不显示成"已保存"。撤销授权只清路径，**不删已写出的文件**（删用户文件是我们不该做的事） |

## D47（2026-10-17）B01 持久化中断窗口修复：原子替换 + 失败不可静默

- **任务**：B01（安全债/数据一致性）。
- **决定**：
  1. 新增 `src/core/persist-io.js` 纯函数模块：`atomicWriteSync` / `atomicWriteJsonSync`（fs 注入可单测）。写盘序列恒为「写 tmp → rename 直接替换」，**任何失败路径都不碰原文件**——失败的结果是"停留在上一版"而不是空。POSIX rename(2) 与 Windows MoveFileExW(MOVEFILE_REPLACE_EXISTING) 本就是单次原子操作，旧实现的"先 unlink 原文件再 rename"纯属自找窗口。
  2. `persist.js` 的 `writeJsonSoon` 与 `flushPersist` 全部改走该原子写；`flushPersist()` 返回 `{ok, written, failed}` 逐文件结果，**调用方必须检查**（ledger-actions / disposeAgent）。
  3. 写盘失败落 `userData/persist-warnings.json`（保留最近 20 次），`index.js` whenReady 调 `consumePersistWarnings()` 如实打到日志（一次一提示，读完即清）。沉默的写失败比写失败本身更糟——用户会以为"她已经记住了"。
  4. `ledger-actions.js` 的 scrub/correct 在 flush 失败时抛错：六个下游清完了却没落盘，绝不能放行 ledger.forget/correct。失败时账本状态保持原样，用户可重试。这堵上 TASKS 里"伪报成功"的口子。

## D57（2026-10-18）取景二次校准：修「只剩头和肩」的位移根因 + 按用户参考图缩小

- **任务**：用户报「画面只显示一个肩膀和头部」要求修正为肚脐以上完整上半身（头、双肩、双臂上段、胸、腰腹到肚脐），并点名要说明「是哪项参数导致可见区域过小」；第一轮修复后用户看对比页反馈「当前还有点大，按参考图来」（参考图 895×1207，实测头顶留白 26%、主体居中、底部裁到腰贴底）。
- **根因（用户点名要的答案）**：**Z 轴容器的 `position` 与 `pivot` 不是同一个点**。支点设在颈肩（`DEPTH_PIVOT_FY=0.23`），position 却写了锚点（带底 0.48）——pixi 的净位移 = `position − pivot`，于是整只模型被往下推 `(0.48−0.23)×7000×s ≈ 182~210px`，推掉的正好是肚脐以上那一段。证据：修复前四个场景（含 full 档）的像素内容全部贴画布底（内容行 473~644 / 450~644 / 426~644 / 511~644），连全身档都只剩半截——不是取景参数太小，是整体被平移了。
- **决定**（四项）：
  1. `live2d.js` 的 `zContainer.position` 改为与支点同一个点（`py − off + dy`），缩放中心不动、只叠 dx/dy，才是"绕颈肩缩放"。
  2. Maine 取景带横向 `0.255~0.83` → **`0.196~0.792`**：`scripts/probe-upper-body.mjs` 逐行像素剖面实测上半身横向 fx∈[0.218, 0.769]、中心 0.494——旧口径 [0.273, 0.813] 是位移 bug 时代测的（中心偏右 0.049），左缘裁掉美术 0.037 且镜像偏移双倍（实测偏左约 46px）。`test/frame.test.js` 的过时断言同步改新实测值。旧值判据"全身横向"也该弃用：实测全身与上半身横向几乎相同。
  3. 镜像水平补偿：`fitBand` 的 x 按**未翻转**带算（减 centerOffset 摆正偏心美术），`scale.x` 取负翻转后偏心方向也翻，少补一次偏 `2·centerOffset·scale` → `model.x = fit.x + (mirror ? 2·co·s : 0)`。
  4. `STANDARD_BOX {300,480}` → 第一轮 `{386,560}`（不裁手臂的几何最大），用户看后嫌大 → 第二轮 **`{300,560}`**（fit=0.1007）。中途试过 `{322,560}`（对齐参考图 26% 留白的精确解）但撞上「工作台与桌宠同比例」的既有承诺：工作台面板 300 宽的 contain=0.10067 是**所有界面瓶颈**，标准盒一旦大于它两界面就差 7%。最终三档头顶留白 47%（基准）/ 39%（日常 1.15）/ 31%（待机 1.32，用户最常见），比参考图略疏朗、方向一致。
- **关键纪律**：
  - **pixi 的 `position − pivot` 是净位移陷阱**：两个属性想表达"同一点 + 绕它变换"时必须写成同一个点，各写各的坐标就变成整体平移。
  - `model.getBounds()` 报的是**声明画布矩形**（pixi-live2d-display 未重写），不是真实美术范围——量化画面必须靠 `snapshotDataURL()` 的 alpha 像素。
  - `fitBand` 的镜像语义缺口：mirror 只翻 `scale.x`，fit.x 的偏心补偿不跟着翻——以后凡"fit 里减了一个与美术朝向有关的量"都要问一句翻转后该不该取反。
  - `verify-frame.mjs` 是最后一个漏 `NAGI_RENDERER_SANDBOX=0` 的起实例脚本（D40 同款问题："桌宠页未就绪"假失败）——已补，至此起 Electron 的脚本全部自带开关。
- **依据**：`npm run build` 退出 0；`verify:frame` **45/45**、`verify:depth` **38/38**、`verify:face` **10/10**（E 项首跑 0.3% 为偶发采样抖动，复跑 2.3% 过）；单测 frame **18/18**（更新过时断言）、depth-motion + face-expression **47/47**。探针实测（430×645，用户设置档）：头顶 y 150→254、覆盖率 39.7%→24.6%（日常档）；待机档头顶 y 77→198、覆盖率 50.2%→31.1% 且不再裁手臂；镜像后美术中心 190 ≈ 可用区中心 193。
- **工具**：新增 `scripts/probe-bust-framing.mjs`（四场景抓帧 + alpha 包围盒 + ASCII 轮廓图，临时探针保留）与 `scripts/probe-upper-body.mjs`（上半身横向剖面）。
- **未验证**：用户真机肉眼确认（对比页已发布 https://nagi-demo.app.workbuddy.host/ ，含参考图对照与三档前后对比）。
- **影响**：桌宠/工作台/设置三处立绘同时变小约 22%（相对第一轮）或回到接近 D55 前的绝对尺寸但构图正确（头到肚脐完整、水平居中、无位移）；无资源、造型、配色改动。
