## 2. 两个缺口（需要口径，不是补几行代码就行）

- **便签**（`notes.json`）：CONTRACTS §11.1 已明确要求「含被遗忘源内容则一并处理或标已删」，
  而当前 `scrub()` 完全没碰它 → 这是**契约内的实现缺口**，不是可选项。
  需要口径的是"一并删除"还是"标已删"（删除会改动她写给用户的话，属于产品取舍）。
- **承诺簿**（`promises.json`）：§11.1 未列，属蓝区自查出的**超出契约**风险。
  它记录"她答应过的事"，可能含被遗忘事件的摘要。清掉=她忘了答应过什么；
  不清=她仍记得"答应过一件事"但说不出内容。要不要处理，请绿区定，我不自行判定。

蓝区不自行判定这两处，按 §7 契约流程由绿区给规格、作者裁决后我再接。

## 3. 明确不覆盖的部分（契约已要求"单独授权"）

- **已导出到电脑的文件**（日记导出、年鉴导出）：本地遗忘不会追回用户自己另存的文件；
- **系统通知历史**（Windows 通知中心）：已派发的通知条目无法由应用删除；
- **云端副本**：用云端模型时，内容已随请求离开本机，撤回只能删本地，不能删远端。

这三点必须在告知文案或验证记录里如实说明，不能承诺"忘了就不存在了"。

## 4. 端到端验证建议（给绿区写 §3.5 用）

1. 造一条经历 → 确认它出现在**五处**（历史 / 记忆 / RAG / 日记或流水 / 年鉴）；
2. 执行 forget → 五处都不可引用：`rag.recall()` 无关命中、`memoryLines()` 无、日记/流水文件无、年鉴无；
3. **重启后**再来一遍检索（防"内存清了但盘上还在"）；
4. **后台生成**（日记定时任务）跑一轮后，旧内容不得被重新生成或重新嵌入；
5. 反向断言：同一时间窗内**其他**经历不受影响（不能一忘全忘）。
