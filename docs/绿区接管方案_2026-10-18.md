# 绿区接管方案（2026-10-18）

## 1. 接管决定与边界

作者已要求 Codex 全权接管豆包原负责的绿区工作。自本记录起，绿区的规格编写、评测执行、红蓝区交付对账和验收状态维护由 Codex 负责。历史文档中的「豆包」保留为当时作者署名；新记录以「绿区（Codex 接管）」署名。红区架构实现、蓝区常规实现仍按任务卡分工；绿区负责给出可检验的输入与结论，并及时回填 TASKS、CONTRACTS、EVAL、HANDOFF、PENDING-CODEX。

不改已冻结的作者裁决。P1-07 已由作者指示暂缓，保留规格与已发现的差异，恢复前不把它计作通过或擅自重启实现。B1 Windows 通知中心 toast 缺设备层证据，仍标待验。

## 3. 执行顺序

### 第一批：封存与纠偏

1. 审校上述绿区未提交差异，检查与已冻结裁决、现有代码、EVAL §0/§3.9 计分口径是否冲突；将有效规格单独提交并记录哈希。特别统一六维评分名称，避免同一轮出现两套量表。
2. 修复 D9 脚本的真模型请求捕获、超时退出、隔离 profile 清理和结果元数据；真模型所需密钥只经环境变量或隔离密钥存储，不写入记录。保留原始假桩结果并明确标为「结构烟测」。
3. 建立「任务 ID → 契约 → 断言 → policy/mock-io/device 证据 → 状态」对照。缺层、跳过或只凭提交说明的一律待验；旧对账条目作为历史记录，不覆盖新结论。

### 第二批：完成阶段 2 绿区交付

1. P2-02 D9：用同一版本、提供商、模型、设置与上下文快照跑 8 高频场景各 2 次；保存去敏的输入、输出、时延、失败与重试次数；按统一六维量表逐条人工评分并盲看对照。任何红线命中即该轮不通过。真模型不可用时保留「待验」，不拿假桩代替。
2. P2-06 C5：读承诺簿的数据引用与清理路径，写清遗忘后承诺应保留何种最小履约记录、何时彻底失效、如何防后台任务复活；把待作者裁决的产品选择与可直接实现的事实分开。按 FORGET/RESTART/BG 证据逐项复核，C5-EXPORT-01 挂 P3-08 保持待验。
3. P2-05/P2-08：为 B7/B9 建立可执行的边界检查与破坏性验证清单；复查 B8 可见状态、D2 意图与 D8 长期一致性是否有对应证据。对蓝区 `1f973a3` 之后的交付按证据独立复核，发现差异写入 PENDING-CODEX 并指定实现归属。

### 第三批：给阶段 3 施工提供规格

1. P3-01 D3：基于现有 ledger/yearbook/锚点定义关系事件的来源、确认、引用、纠错、遗忘与隐私约束，不建平行事实库。
2. P3-06 C3：定义生成前预算、生成后授权/新鲜度/预算重验，事件 ID/epoch 取消语义及可观察的交错测试。
3. P3-08 C5 导出：写明用户发起、字段来源、主观/模拟/已删标记、外部副本边界和 C5-EXPORT-01 的 mock-io 验收。与蓝区实现联动后再关单。
4. 阶段 3 的 D4、D6 已有规格，施工时按 EVAL §3.2/§3.3 对账，重点查「先别讲道理」和不机械说「我能帮你什么」等红线。

## 4. 交付与关单规则

- 每张绿区卡交付：一段明确规格、一组可判定断言、一份运行证据或「待验」原因、TASKS 状态、HANDOFF 摘要。涉及实现阻塞时在 PENDING-CODEX 写最小复现、影响与归属。
- 每轮评测必须固定版本与模型，保留原始失败样本；对照同一 EVAL 场景集判断是否改善。分数不能冲掉红线，假桩不能证明主观质量，程序派发不能证明 Windows toast 可见。
- 只在全部必需证据齐全且与契约相符时标「通过」。需作者裁决的产品选择写成具体选项和影响，现有裁决 A/B 继续生效。
