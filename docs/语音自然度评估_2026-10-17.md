## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 现在是什么水平 | **借用了工业级神经 TTS，但只用了它 15% 的能力。** 综合 MOS 估 **3.4–3.9 / 5**（真人 4.6+，顶级商用 4.2–4.5） |
| 最大瓶颈 | 不是"音质差"，是**韵律控制维度只有 3 个整句全局标量** + **48kbps MP3 容器** + **句级拼接无跨句韵律** |
| 不大改能到多少 | **4.0–4.2**。主要靠：输出码率、`<break>`、`mstts:express-as` 风格、归零 rate 偏移、句间换气 |
| 再往上必须突破 | 音色所有权（需自有干音 + 少样本克隆）、韵律可控建模、声码器与采样率、评测闭环 |
| 最反直觉的一条 | **换自有音色会让绝对音质下降。** 用开源 SoVITS 换掉晓晓，MOS 大概率从 ~4.1 掉到 3.6–4.1，换来的是身份与可控性 |
| 个人开发者的真上限 | **4.0–4.2（借用音色）/ 3.6–4.1（自有音色）**。GPT-Live 那类全双工 + 副语言，**做不到** |

## 1. 现状：完整技术路线梳理

### 1.1 语音合成（TTS）—— 项目内**没有任何 TTS 模型**

`[事实]` 全部走外部服务，本地零模型：

| 引擎 | 实现 | 状态 |
|---|---|---|
| **edge-tts**（默认） | `main/voice/edge.js` 自建 WebSocket 客户端，直连 `wss://api.msedgeservices.com/tts/cognitiveservices/websocket/v1`，带 `Sec-MS-GEC` = SHA256(窗口化 Windows FILETIME + TrustedClientToken) 签名 + `Sec-MS-GEC-Version` | **在用** |
| **SAPI** | `main/voice/sapi.js` + `resources/voice/tts-sapi.ps1`（PowerShell 桥） | 兜底，音质"机器朗读" |
| cloud | 仅注册表占位 | 未实现 |
| **GPT-SoVITS** | 仅注册表占位；`main/voice/index.js` 里 `gptsovits: false` **硬编码** | 未实现 |

`[事实]` 输出格式常量：`audio-24khz-48kbitrate-mono-mp3`。
`[事实]` SSML 只有一层（edge.js `buildSsml`）：

```xml
<speak ...><voice name='zh-CN-XiaoxiaoNeural'>
  <prosody rate='-10%' pitch='-2%' volume='100%'>文本</prosody></voice></speak>
```

**没有** `<break>`、**没有** `<emphasis>`、**没有** `mstts:express-as`（风格）。

`[事实]` 关键遗漏：`configMessage()` 里 `metadataoptions` 把
`sentenceBoundaryEnabled` 和 `wordBoundaryEnabled` 都设成了 `'false'` ——
**服务端本来会回词级时间戳，被主动关掉了。** 这是本次评估发现的最大"白送的能力"。

### 1.2 语音识别（ASR）—— 有离线模型

`[事实]` `sherpa-onnx v1.13.8`，`win-x64-shared-MD-MinSizeRel-**no-tts**` 构建（注意：
**明确选了不带 TTS 的包**），模型 `sherpa-onnx-paraformer-zh-small-2024-03-09`（int8 量化）。
常驻 WebSocket 子进程（模型只加载一次，加载 4.3–4.8s，靠预热挪到后台），单次识别约 **440ms**，
空闲 5 分钟回收，约 150MB 内存。降级到 SAPI。

### 1.3 韵律建模 —— 三个标量，整句全局

`[事实]` 两条路径（`presence.voiceProfileEnabled` 默认 **false** → 实际生效的是第一条）：

1. `MOOD_SPEECH`（engines.js）：6 种情绪 → `rate`/`pitch` 偏移
   `calm(0,0) smile(+4,+2) joy(+8,+4) puzzled(-2,+3) worry(+6,-2) pout(-8,-4)`
2. `VOICE_PROFILE`（voice-profile.js，BLUE-1）：情绪 × intensity + 昼夜时段 + toneTag → 同 3 维

`[事实]` 最终落到引擎的就是 `{rate, pitch, volume}` 三个**整句全局**标量。
`[事实]` 基准声线 `NAGI_VOICE.edge = { XiaoxiaoNeural, rate: -10, pitch: -2, volume: 100 }`。

**这意味着什么**：情绪 = "同一个人说得快一点/慢一点、调门高一点/低一点"。
真人的情绪体现在 **F0 动态范围扩大、语速方差增大、停顿模式改变、频谱倾斜（嗓音质地）变化** 四件事上，
全局 pitch 偏移**一件都模拟不了**。

`[事实]` 附带代价：`rate: -10` 意味着**每一句都在做 10% 时间拉伸**，本身引入轻微 artifacts；
且情绪叠加后最大可达 rate −18%，拉伸更明显。

### 1.4 音质后处理 —— **没有**

`[事实]` 全链路无任何音频后处理：无限幅、无 loudness 归一化、无 EQ、无 de-ess。
`core/voice/wav.js` 里的钳位/重采样/静音裁剪**只服务于录音侧（ASR 输入）**，不碰 TTS 输出。
输出 MP3 直接交给渲染层 `<audio>` 播放。

### 1.5 训练与推理流程

`[事实]` **训练：零。** 项目里没有任何训练代码、训练数据、微调流程。
`[事实]` 推理：TTS 是"分句 → 逐句 HTTP/WSS 请求 → 拿完整音频"（`edgeSpeakOnce` 收齐 `turn.end` 才返回，
不是流式）；渲染层播第 1 句的同时预取第 2 句（`startSpeech` → `pullUtterance(i)` 的 pull 模式）。
`[事实]` 分句器 `minChars=6, maxChars=60`，硬标点（。！？…；）优先，超长退到软标点（，、：）。
`[事实]` 口型是**音节估算**（`estimateUnits`：中日韩按字、英数按字符折半），
`minSlotMs=110`、`gapRatio=0.18`、半正弦包络 + 确定性 hash 抖动。**不是音素级。**

### 1.6 依赖的预训练模型与数据规模

| 用途 | 模型 | 规模 | 来源 |
|---|---|---|---|
| ASR | sherpa-onnx paraformer-zh-small (int8) | ~78–98MB | 公开 release |
| RAG 嵌入 | bge-small-zh（onnxruntime-web） | ~25MB，512 维 | 公开 |
| **TTS** | **无本地模型，纯外部服务** | **0** | — |
| 训练数据 | **无** | **0 小时** | — |

`[事实]` 本机算力：**RTX 5060 / 8GB**（M6 实测文档）。

## 2. 当前水平判定

### 2.1 MOS 估计（推断，需实测确认）

从一个反直觉的起点出发：**晓晓就是微软的工业级神经音色**，和 Azure 卖的是同一族声线。
所以"音质差"不是问题。损耗全在别处：

| 环节 | 影响 | 依据 |
|---|---|---|
| XiaoxiaoNeural 原始音色 @ 24kHz | 基线 ~4.1–4.3 | `[行业参照]` 神经 TTS 独立评测普遍 3.9–4.3 |
| 48kbps MP3 容器 | **−0.2 ~ −0.4** | `[事实]` 24kHz/48kbps 是 Edge 朗读端点档位，高频明显受限 |
| 句级独立合成、跨句韵律断裂 | **−0.2 ~ −0.4** | `[事实]` 每句独立请求，无跨句 coarticulation |
| rate = −10% 全程时间拉伸 | −0.1 ~ −0.2 | `[事实]` |
| 情感表达失真 | −0.1 ~ −0.3（主维度）<br>**−1.0+（情绪匹配专项）** | `[事实]` 3 标量模拟不了情绪 |

**综合 MOS 估计：3.4 – 3.9 / 5**（整体自然度主维度）

对照：

```
真人录音            ████████████████████████ 4.6+
GPT-Live / 顶级商用  █████████████████████    4.2–4.5
Azure 48kHz 满配     ████████████████████     4.1–4.3
凪 当前（调优前）     ████████████████         3.4–3.9   ← 在这里
凪 调优后（预期）     ███████████████████      4.0–4.2
SAPI 兜底（慧慧）    ████████████             2.8–3.2
```

`[推断]` 用户 2026-10-16 的反馈"情绪起伏偏弱、整体过于含蓄"与这张表一致。
DECISIONS 把它归因到角色侧（台词风格），但**语音侧同样有结构性上限**——
把 `VOICE_PROFILE` 表里的数值调大只会让"她说话变快/变尖"，不会让她"听起来更高兴"。

### 2.2 怎么验证（不用听众也能量）

`[事实]` 项目里**没有任何语音质量或延迟的统计**，README 明确写了"不给未经测量的'一秒首响'承诺"。
这是必须先补的洞。三层验证，从便宜到贵：

**A. 客观自动分（当天可跑）**
- 跑开源 **UTMOS**（VoiceMOS Challenge 2022 冠军方案）给当前样本打分，拿到可复现的基线数字
- 用 `parselmouth` / `pyworld` 提 F0，对比真人参考音频的四项：
  - F0 标准差（真人女声均值 ~200Hz 时 std 常 20–40Hz；**全局 pitch 偏移不改变 std** → 一测就知道情绪是真是假）
  - 语速方差（音节/秒）
  - 停顿时长分布
  - 句间静音是否等于"播放器硬接"
- FFmpeg 看 10–12kHz 以上频谱能量，量化 48kbps 的损失

**B. CMOS 主观测试（1 天，n≥15）**
三条件配对比较：真人参考 / 凪当前 / 商用对照，10 句覆盖 6 种情绪，双盲随机序。
这才能给出可信的 MOS 差值，也是判断后面每一次改动"是变好还是变坏"的唯一依据。

**C. 端到端延迟实测**
`[事实]` 渲染层已有 `voiceTrace.firstAudioAt` 埋点，`edgeSpeakOnce` 已有 `firstChunkMs`，
但**没有汇总统计**。补一个脚本，跑 50 次，出 P50/P95。
`[行业参照]` 本地 LLM 首字已有实测（qwen2.5 7B Q4 = 41ms），ASR ~440ms，缺的就是 TTS 那一段。

## 3. 瓶颈（按权重排序）

1. **韵律控制维度不足（最大）** —— 只有 rate/pitch/volume 三个整句全局标量。
   缺：时长模型、F0 曲线、能量曲线、停顿插入、重音。这五项才是"像不像人说话"的核心。
2. **容器码率** —— 24kHz/48kbps MP3。
3. **跨句韵律断裂** —— 每句独立合成，拼接处无 coarticulation，句间停顿由播放器调度决定而非韵律设计。
4. **音色无所有权** —— 晓晓是公共声线，所有用 edge-tts 的应用听起来一样。
5. **情感建模缺失** —— 是"参数偏移"不是"风格建模"，不可通过调表解决。
6. **口型非音素级** —— 视听不一致性会反向拉低主观自然度；而服务端本来提供词级时间戳却被关掉了。
7. **零训练数据** —— 决定了后面所有"训练"路线都还没起步。
8. **无评测闭环** —— 没有它，任何调参都是在黑暗中试。

## 4. 不大改方案：能调到什么程度

全部在现有架构内（改 edge.js 的 SSML 拼装 / 改常量 / 改播放调度），不动引擎、不引本地模型。

| # | 改动 | 位置 | 预期 MOS | 成本 | 备注 |
|---|---|---|---|---|---|
| T1 | 输出码率 48k → **96kbps**（试 24kHz-96k / 48kHz-96k） | `edge.js` `OUTPUT_FORMAT` 一行 | **+0.15~0.3** | 10 分钟 | **性价比最高**，需实测端点接受哪些档位 |
| T2 | 打开 **wordBoundaryEnabled** | `edge.js` `configMessage()` | 间接 +0.1~0.2 | 半小时 | 白送的词级时间戳 |
| T3 | 用 T2 的时间戳做**音素级口型** | `lip.js` + renderer | +0.1~0.2 | 2–3 天 | 视听一致性 |
| T4 | SSML **`<break>`**：逗 200ms / 句 400ms / 省略号 600ms | `buildSsml` + segmenter | +0.1~0.2 | 1 天 | `[行业参照]` edge-tts 确认支持 break |
| T5 | **`mstts:express-as style` + styledegree** 替代全局 rate/pitch | `buildSsml` + voice-profile | **+0.3~0.5** | 1–2 天 | **情绪维度最大单点**。需先实测晓晓支持哪些 style（HA 集成列出 style/styledegree 且注明"仅普通话可用"，可信度较高但仍要实测） |
| T6 | `NAGI_VOICE.edge.rate` 从 −10 **归零**，情绪交给 style | `engines.js` 常量 | 消除拉伸 artifact | 小时级 | 与 T5 配套 |
| T7 | 句间插入 **80–150ms 换气静音** | renderer 播放调度 | +0.1~0.2 | 半天 | 比现在的硬接自然 |
| T8 | 播放侧 **loudness 归一化到 −16 LUFS** | Web Audio 或预计算 | +0.05~0.1 | 半天 | ITU-R BS.1770 |
| T9 | 首句快 / 后续句合并（非首句 `minChars` 提到 ~20） | segmenter / 编排 | +0.05~0.1 | 1 天 | 减少拼接缝隙，同时保住首响 |

**调优后上限：4.0 – 4.2。** 仍然是"借来的声音"——音色不属于凪，情绪仍受限于微软预置的几种 style，
跨句韵律仍无建模。

## 5. 再往上：必须突破什么

### 5.1 音色所有权（门槛在数据，不在算法）
需要少样本克隆：`GPT-SoVITS v4` / `CosyVoice2-0.5B` / `IndexTTS2` / `Fish-Speech`。
`[推断]` RTX 5060 8GB 可跑这些的**推理**（fp16 约 4–6GB 显存）。

**真正的门槛是干音**：稳定克隆需要 30 分钟–2 小时**高质量单人干音**（安静环境、好麦、无混响、无配乐）。
这一步是**录音工程问题，不是模型问题**——算法、代码、算力都已开源，唯独数据得自己产。
`[事实]` 项目当前是零数据。

**代价要说清楚**：开源 SoVITS 的音质**低于**微软工业级神经 TTS。
换自有音色大概率让 MOS 从 ~4.1 掉到 **3.6–4.1**，换来身份与可控性。
想两者兼得需要几十小时高质量单人数据 + 微调——个人开发者做不到。

### 5.2 韵律可控建模
要从"3 个标量"升级到"时长 + F0 曲线 + 能量 + 停顿"可控。
`CosyVoice2` / `IndexTTS2` 已提供文本或音频驱动的风格与**显式时长控制**，是可行路径。
但要做到真正可控，仍需带韵律标注的数据——**开源中文多情感标注数据集稀缺**，这是数据瓶颈。

`[行业参照]` 可用的开源中文语料：AISHELL-3（约 8h / 218 人，Apache 2.0）、
Baker（约 12h 标准女声，许可需确认）、MagicData、diDiSpeech。
这些能支撑"训练一个中性音色"，**支撑不了多情感**。

### 5.3 声码器与采样率
HiFi-GAN 24kHz → BigVGAN 44.1kHz 明显更自然，算力约翻倍。5060 8GB 可行。

### 5.4 端到端延迟
`[推断]` 本地 SoVITS 在 5060 上 RTF 约 0.3–1.5×（非自回归 vs 自回归差异大）。
要保住"首句即响"必须选非自回归方案或做流式切片，**上线前必须实测 RTF 与首句 TTFA**。

### 5.5 评测闭环（最先做）
没有 MOS/CMOS 测量，就无法判断任何改动的真实效果——
2026-10-16 那次"情绪偏弱"的反馈，归因到角色侧还是语音侧至今没有客观依据。
**先建评测，再改参数。**

### 5.6 明确做不到
`[行业参照]` GPT-Live 那类**全双工 + 副语言（笑声/叹气/气息）+ 边听边说**：
需要双流重叠语音训练数据（几乎没有公开中文语料）+ 全双工架构 + 推理基础设施重构。
个人开发者 + 单卡 + 公开数据条件下**做不到**。

## 6. 建议的下一步（按性价比）

1. **建评测**（半天）：UTMOS 打分 + F0/语速/停顿四项统计 + 端到端延迟 P50/P95 脚本
2. **T1 码率**（10 分钟）：一行常量，立刻可听出差值
3. **T2+T3 词级时间戳 → 音素口型**（2–3 天）：能力本来就在，只是被关掉了
4. **T5/T6 风格控制**（1–2 天）：先做一次 style 支持度探测，确认晓晓能接哪些
5. 之后再做 CMOS 复测，拿到可信的前后对比数字

> 全部 1–4 项做完约 1–2 周，预期把综合 MOS 从 3.4–3.9 拉到 4.0–4.2。
> 第 5 项的测量数据是判断"是否值得走 5.1 自有音色"的决策依据。
